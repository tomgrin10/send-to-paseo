# Bridge contract v1

The single integration point between the Chrome extension and the Paseo plugin.
**Both sides implement exactly this. Neither side may change it unilaterally.**

- Transport: HTTP/1.1, JSON bodies, UTF-8.
- Bind address: `127.0.0.1` only. Default port `7788`.
- Base URL: `http://127.0.0.1:7788`
- All paths prefixed `/v1`.

## Auth

Every endpoint except `GET /v1/ping` requires:

```
Authorization: Bearer <token>
```

The token is generated by the plugin on first run (32 random bytes, base64url) and stored
`0600` at `$PASEO_HOME/plugin-data/send-to-paseo/settings.json`. The user copies it from the
plugin's Paseo surface into the extension options page.

Missing/invalid token → `401` with `{"error":{"code":"unauthorized","message":"..."}}`.

## Origin and Host rules (security-critical)

The bridge MUST:

1. Reject any request whose `Origin` header is present and does **not** start with
   `chrome-extension://` → `403 forbidden_origin`. This applies to the preflight **and** the
   real request. (CORS alone only prevents a page from *reading* a response; the request would
   otherwise still fire and cause the side effect. Requiring `Authorization` forces a preflight,
   and failing that preflight means the request never executes.)
2. Reject any request whose `Host` header is not `127.0.0.1:<port>` or `localhost:<port>`
   → `403 forbidden_host`. Closes DNS rebinding.
3. On success, echo CORS headers:
   ```
   Access-Control-Allow-Origin: <the request's chrome-extension:// origin>
   Access-Control-Allow-Methods: GET, POST, OPTIONS
   Access-Control-Allow-Headers: Authorization, Content-Type
   Access-Control-Max-Age: 600
   Vary: Origin
   ```
   Do **not** send `Access-Control-Allow-Credentials`.
4. Requests with **no** `Origin` header (e.g. `curl`) are allowed, so the bridge stays testable
   from the CLI. They still require the bearer token.
5. Cap request bodies at 64 KiB → `413 payload_too_large`.
6. Rate limit: max **60 requests / 10 s** per origin → `429 rate_limited`.

   Raised from 30 after implementation: the extension's `contract`-mismatch gate re-pings before
   every resolve and send (deliberately uncached, so a plugin updated while the composer is open
   cannot be sent to), which costs 4 requests per completed send. 30/10 s left only ~7 sends per
   window. 60 gives ~15 while still bounding the endpoint. The limit is defence-in-depth here —
   the bridge is loopback-only and token-gated — so `GET /v1/ping` stays counted rather than
   exempt, to keep the bound total.

## Shared types

```ts
type Forge = "github";

interface PrRef {
  forge: Forge;
  owner: string;      // "acmegizmos"
  repo: string;       // "gizmo-poc"
  number: number;     // 942
}

interface ErrorBody {
  error: {
    code: string;     // stable machine code, see table below
    message: string;  // human sentence, safe to show in the popover
    hint?: string;    // concrete next step, e.g. "Run: gh auth login"
  };
}

interface Provider {
  id: string;         // "claude/claude-opus-5" — ALWAYS `provider/model`
  label: string;      // "Opus 5"
  isDefault: boolean; // exactly one entry, the plugin's effective default
}

interface Mode {
  provider: string;      // BARE provider id: "claude", not "claude/claude-opus-5"
  id: string;            // "auto", "bypassPermissions"
  label: string;         // "Auto mode", "Bypass"
  isDefault: boolean;    // THIS PROVIDER's default mode, not one per list
  isUnattended?: boolean; // runs without asking permission
  colorTier?: string;    // "safe" | "moderate" | "planning" | "dangerous"
}
```

**Mode ids are per provider.** Claude offers `plan`, `default` (which is the UI's
"Always Ask"), `acceptEdits`, `auto` and `bypassPermissions`; Codex offers `auto`,
`auto-review` and `full-access`. The same string can exist under two providers and
mean different things, and most strings exist under only one. A consumer MUST filter
`modes` by the bare provider of the `provider/model` it is about to send, and MUST NOT
carry a mode selection across a provider change. `isDefault` marks each provider's own
default, so more than one entry in the flat list is flagged.

Unattended modes are **listed, never hidden**. Hiding "Bypass" would not make it safer,
it would make it invisible; both sides surface it and mark it instead. `colorTier` and
`isUnattended` exist so a UI can do that without hard-coding provider knowledge.

### Error codes

| code | HTTP | Meaning | Extension shows |
| --- | --- | --- | --- |
| `unauthorized` | 401 | bad/missing token | "Not paired with Paseo" + link to options |
| `forbidden_origin` | 403 | non-extension origin | (never reached in practice) |
| `forbidden_host` | 403 | bad Host header | generic |
| `bad_request` | 400 | schema validation failed | generic + message |
| `payload_too_large` | 413 | body > 64 KiB | "Message too long" |
| `rate_limited` | 429 | too many requests | "Slow down" |
| `project_not_found` | 404 | repo isn't a registered Paseo project | message names the repo + hint to add it |
| `pr_not_found` | 404 | forge lookup failed | message names the PR |
| `forge_unauthenticated` | 502 | `gh` missing or not logged in | hint: `gh auth login` |
| `workspace_create_failed` | 502 | checkout-pr failed | message carries the underlying reason |
| `agent_create_failed` | 502 | daemon refused | message carries the underlying reason |
| `daemon_unreachable` | 503 | plugin can't reach its daemon | "Paseo daemon unreachable" |
| `internal` | 500 | unexpected | generic |

Auth **optional**. Used by the options page's "Test connection" and by the content script to
decide whether to render the button at all.

```json
  "name": "send-to-paseo",
  "version": "0.1.0",
  "contract": 1,
  "daemon": { "reachable": true, "version": "0.7.0", "serverId": "srv_Ab3xY9pQ2mNt" },
  "paired": true,
  "providers": [
    { "id": "claude/claude-opus-5", "label": "Opus 5", "isDefault": true },
    { "id": "claude/claude-sonnet-5", "label": "Sonnet 5", "isDefault": false }
  ],
  "modes": [
    { "provider": "claude", "id": "plan", "label": "Plan Mode", "isDefault": false, "colorTier": "planning" },
    { "provider": "claude", "id": "default", "label": "Always Ask", "isDefault": false, "colorTier": "safe" },
    { "provider": "claude", "id": "acceptEdits", "label": "Accept File Edits", "isDefault": false, "colorTier": "moderate" },
    { "provider": "claude", "id": "auto", "label": "Auto mode", "isDefault": true, "colorTier": "moderate" },
    { "provider": "claude", "id": "bypassPermissions", "label": "Bypass", "isDefault": false, "isUnattended": true, "colorTier": "dangerous" },
    { "provider": "codex", "id": "auto-review", "label": "Auto-review", "isDefault": true, "colorTier": "moderate" }
  ]

```

`daemon.reachable: false` still returns 200 — ping reports status, it doesn't fail.

### Token validation on ping

- **No `Authorization` header** → 200 with `paired: false`, `providers: []` and `modes: []`. This
  is the unauthenticated liveness check; it must keep working so the options page can distinguish
  "bridge down" from "bad token".
- **`Authorization` present and valid** → 200 with `paired: true` and the full `providers` and
  `modes` lists.
- **`Authorization` present and invalid** → `401 unauthorized`.

This is what makes "Test connection" able to actually validate a pasted token, and gives the
options page a PR-independent source for the default-provider picker. `providers` and `modes`
here are the same shape as in `/v1/resolve`; `modes` follows exactly the same auth rule as
`providers`.

## `POST /v1/resolve`

Called when the popover opens, before the user types. Must be fast; it may not create anything.

**Request**
```json
{
  "forge": "github",
  "owner": "acmegizmos",
  "repo": "gizmo-poc",
  "number": 942,
  "stackPrNumbers": [949, 948, 947, 946, 945, 943, 941]
}
```

`stackPrNumbers` is optional and may be empty. The extension excludes the PR itself, but the
bridge MUST tolerate a self-inclusive list and filter it, rather than rejecting — a scrape of a
third-party page is not something to be strict about. Best-effort overall: if resolving them is
slow or fails, the bridge returns candidates without rank-2 entries rather than erroring.

**As of 2026-09-01 these numbers are a supplement, not the source of truth.** The bridge derives
the stack from the forge itself: a Graphite stack is a real `base` -> `head` chain on GitHub, so
one `gh pr list` rebuilds the whole stack and the bridge walks the connected component containing
this PR. That removed a real failure: Graphite's stack panel collapses long stacks ("3 of 9, 2
hidden"), so a scrape could omit the very sibling the user's workspace was sitting on. The field
is still honoured for members the graph did not find — in practice a stack PR that is closed or
merged — and sending an empty list is now fully supported.

**As of 2026-09-02 stack discovery also covers merged and closed pull requests.** A branch whose
PR has merged is still a branch of the stack as far as a user's workspace is concerned, and the
open-PR graph could not see it at all: it is absent from `--state open`, and when its head branch
is deleted on merge GitHub *retargets* the child PR's base to trunk, destroying the `base` ->
`head` edge that joined them. So the bridge now has three passes, each reached only when the
previous one left a workspace unexplained — the open-PR graph, then merged and closed PRs, then
purely local `git` ancestry (a stack branch below this PR is by definition an ancestor of it).
The last of those can even recognise a stack branch with no PR at all, which is why
`stackPrNumber` is not guaranteed on a rank-2 candidate. All of it is still best-effort: a bridge
that cannot answer returns fewer rank-2 entries, never an error.

**200**
```json
{
  "pr": {
    "number": 942,
    "title": "GIZ-1133: Legacy tally engine retirement #3 - ...",
    "headBranch": "giz-1133-widget-backed-inventory-audit-rule",
    "baseBranch": "main",
    "state": "OPEN",
    "url": "https://github.com/acmegizmos/gizmo-poc/pull/942"
  },
  "project": {
    "projectId": "remote:github.com/acmegizmos/gizmo-poc",
    "name": "acmegizmos/gizmo-poc",
    "path": "~/Projects/gizmo-poc"
  },
  "candidates": [
    {
      "kind": "existing",
      "workspaceId": "wks_4d1a8b7c2e0f9351",
      "label": "brawny-dodo",
      "branch": "giz-1133-widget-backed-inventory-audit-rule",
      "cwd": "~/.paseo/worktrees/pj4k2wxb/brawny-dodo",
      "isolation": "worktree",
      "rank": 1,
      "reason": "exact",
      "agentCount": 2
    },
    {
      "kind": "existing",
      "workspaceId": "wks_8b2c1e9f4a730d65",
      "label": "plucky-otter",
      "branch": "giz-1132-retire-legacy-cache-flag",
      "cwd": "~/.paseo/worktrees/pj4k2wxb/plucky-otter",
      "isolation": "worktree",
      "rank": 2,
      "reason": "stack",
      "stackPrNumber": 941,
      "stackPrState": "merged",
      "agentCount": 0
    },
    {
      "kind": "create",
      "label": "Create worktree for PR #942",
      "branch": "giz-1133-widget-backed-inventory-audit-rule",
      "rank": 4,
      "reason": "create"
    }
  ],
  "defaultCandidateIndex": 0,
  "providers": [
    { "id": "claude/claude-opus-5", "label": "Opus 5", "isDefault": true },
    { "id": "claude/claude-sonnet-5", "label": "Sonnet 5", "isDefault": false }
  ],
  "modes": [
    { "provider": "claude", "id": "auto", "label": "Auto mode", "isDefault": true, "colorTier": "moderate" },
    { "provider": "claude", "id": "bypassPermissions", "label": "Bypass", "isDefault": false, "isUnattended": true, "colorTier": "dangerous" }
  ],
  "resolvedModeId": "auto"
}
```

`pr.headBranch` / `pr.baseBranch` come from `gh`, so `baseBranch` is the real GitHub base — the
parent PR's head branch inside a stack, or trunk at the bottom. The `graphite-base/942` ref that
Graphite's own UI displays is display-only and never appears here.

`candidates` is sorted ascending by `rank`, and always contains at least the `create` entry.

- `rank: 1` / `reason: "exact"` — workspace HEAD == PR head branch
- `rank: 2` / `reason: "stack"` — workspace HEAD is another branch in this stack, whatever the
  state of that branch's own pull request. Carries `stackPrNumber` **when the branch has a pull
  request**, and `stackPrState` when that PR is not open.
- `rank: 3` / `reason: "project"` — any other workspace in the project
- `rank: 4` / `reason: "create"` — the synthetic create option

The reason and rank sets are **closed**. A merged or closed stack branch is still
`reason: "stack"`, `rank: 2`; it does not get a reason of its own, because an extension built
against an earlier version of this contract renders an unrecognised reason as a raw string.

`stackPrState` is `"open" | "merged" | "closed"`, and is **omitted when the state is open** —
which is exactly what an extension that predates the field already assumes, and what makes it
additive. It is present only alongside `stackPrNumber`: a rank-2 candidate can have neither,
which means the bridge established that the branch belongs to the stack (from local commit
ancestry) but the branch has no pull request of its own. A consumer MUST NOT read a missing
`stackPrState` as "unknown".

`defaultCandidateIndex` indexes into `candidates`. The bridge picks, in order:

1. the `rank: 1` exact branch match, else
2. the best `rank: 2` stack match, else
3. the `rank: 4` create entry.

"Best" among rank-2 candidates is, in order:

1. an **open** stack PR's branch before a merged or closed one, and both before a stack branch
   with no PR at all. A live sibling is somewhere work is still happening; a merged branch is
   history the stack has already been restacked past. This comparison comes *first*, so an open
   sibling eight hops away beats a merged one at one hop;
2. fewest hops along the `base` -> `head` chain. A hop count measured from GitHub's own graph
   always beats one the bridge could not measure, and both beat membership inferred from local
   git ancestry alone;
3. lowest `stackPrNumber`, then label order.

`rank: 3` is deliberately never a default: an unrelated workspace in the same project is a worse
guess than a fresh worktree. Preferring rank 2 over create matters because one workspace per
*stack* is a normal way to work — you open PR #4 while the worktree sits on PR #7's branch — and
defaulting to create silently proposed a second checkout of a stack already open. Extending that
to *merged* branches matters for the same reason: after the bottom of a stack merges, the
workspace parked on it was falling all the way through to "create a worktree", proposing a second
checkout of a stack the user already had open.

`defaultCandidateIndex` is always a valid index. Whatever the bridge can or cannot determine
about the stack, `candidates` ends with the `create` entry and that is the fallback.

`modes` is the same flat, provider-tagged list as on `/v1/ping`.

`resolvedModeId` is the mode a `POST /v1/send` **would actually use right now** for the
`isDefault` provider, after the plugin's whole resolution chain (see `/v1/send` below). It is
`null` when the chain resolves to nothing and the plugin would omit the field from
`agents.create` entirely. It exists so the popover can preselect what will happen rather than
guess: preselecting `modes[].isDefault` would ignore a followed profile, and preselecting the
first entry would silently pick "Always Ask".

`resolvedModeId` is scoped to the default provider. When the user changes the provider in the
popover, the extension must re-pick from `modes` filtered to the new provider — the resolved
value from a different provider is not transferable.

Per the product decision, the extension **always shows the picker and requires an explicit
Send**; it never auto-creates silently, whatever the default is.

## `POST /v1/send`

Creates the agent. This is the only mutating endpoint.

**Request**
```json
{
  "forge": "github",
  "owner": "acmegizmos",
  "repo": "gizmo-poc",
  "number": 942,
  "prompt": "Fix merge conflicts",
  "target": { "kind": "existing", "workspaceId": "wks_4d1a8b7c2e0f9351" },
  "provider": "claude/claude-opus-5",
  "modeId": "auto",
  "pageUrl": "https://app.graphite.com/github/pr/acmegizmos/gizmo-poc/942/GIZ-1133-..."
}
```

`target` is one of:
```ts
{ kind: "existing", workspaceId: string }
{ kind: "create" }                          // create a worktree via checkout-pr
```

`prompt` is required, 1..16000 chars after trim. `provider` optional — falls back to the plugin's
configured default. `modeId` optional, bounded exactly like `provider` (1..200 chars).
`pageUrl` optional, used only to enrich the agent's opening prompt.

### Permission mode resolution (`modeId`)

The plugin resolves the agent's permission mode in this order, and **validates every candidate
against the chosen provider's advertised `modes[]` before accepting it**:

1. `modeId` on the request — the popover's explicit choice, which always wins;
2. the `modeId` of the Paseo agent profile the plugin is configured to follow, read live from
   `daemon.agentProfiles` on every send;
3. the plugin's own configured default mode;
4. the chosen provider's `defaultModeId` as reported by the daemon;
5. nothing — the field is omitted from `agents.create` and Paseo applies its own default.

A candidate the provider does not advertise is **skipped, logged, and the chain continues**. It
is never an `agent_create_failed`: mode ids are per-provider, so a stored `bypassPermissions`
becomes meaningless the moment the user picks Codex, and a stale id must not break every send.
The same rule covers a profile id that no longer exists — the profile is ignored, the send goes
through.

`provider` and `modeId` on the request are independent. Naming a `provider` does **not** stop
the profile from supplying a `modeId`, and naming a `modeId` does not stop the profile from
supplying the provider. But an explicit `provider` always beats the profile's provider: the
popover's visible choice is never silently overridden.

Before this existed the plugin sent `config: { provider }` and nothing else, so Claude's
provider fell back to `modeId: "default"` — the UI's **"Always Ask"** — and every agent the
plugin created came up in the strictest mode regardless of the user's own default.

**200**
```json
{
  "ok": true,
  "agentId": "agt_...",
  "workspaceId": "wks_...",
  "workspaceCreated": false,
  "workspaceLabel": "brawny-dodo",
  "branch": "giz-1133-widget-backed-inventory-audit-rule",
  "deepLink": "paseo://h/srv_Ab3xY9pQ2mNt/agent/agt_...",
  "title": "PR #942 · Fix merge conflicts",
  "dryRun": false
}
```

`dryRun` is always present. `true` only when the plugin is running with
`SEND_TO_PASEO_DRY_RUN=1` (see "Test mode"), in which case nothing was created and
`agentId`/`workspaceId` are synthetic.

`branch` is the branch **actually checked out** in the target workspace, which is not always
equal to `pr.headBranch`. When `target.kind` is `create` and a local branch of the PR head
branch's name already exists in the repository, Paseo's `checkout-pr` creates a uniquely
suffixed local branch (`giz-1133-…-rule-1`) tracking `origin/<pr.headBranch>`; the commit and
upstream are the PR's, only the local label differs. The extension must not assert
`send.branch === resolve.pr.headBranch`.

### Deep link format (verified — do not guess this)

`deepLink` MUST produce exactly the format Paseo's own `buildAgentDeepLink` produces:

```text
paseo://h/<encodeURIComponent(serverId)>/agent/<encodeURIComponent(agentId)>
// => "paseo://h/srv_Ab3xY9pQ2mNt/agent/agt_example123"
```

Both segments are trimmed first; an empty `serverId` or `agentId` is an error, not a
link. The plugin implements this itself (`buildAgentDeepLink` in `contracts.shared.ts`)
rather than importing `@getpaseo/protocol/agent-deep-link`, because `@getpaseo/protocol`
is not a host-provided module and importing it breaks `paseo plugin add` — see
`plugin/VERIFICATION.md` §18. The two were proved byte-identical across 14 cases,
including double-encoding and slash-bearing ids.

The shape is `paseo://h/<serverId>/agent/<agentId>`. The `serverId` is required — get it from the
daemon (`paseo daemon status --json` → `serverId`, also in `GET /api/status`). Verified by
round-tripping through the package's own `parseAgentDeepLink`; the plausible-looking
`paseo://agent/<agentId>` parses to `null` and would be a dead link.

The extension treats `deepLink` as an opaque string and must not construct it itself.

### Prompt composition

The plugin prepends a short context header so a terse instruction is actionable:

```
[Sent from Graphite — github/acmegizmos/gizmo-poc PR #942]
Title: GIZ-1133: Legacy tally engine retirement #3 - Make the inventory-audit rule widget-backed
Branch: giz-1133-widget-backed-inventory-audit-rule -> main
PR: https://github.com/acmegizmos/gizmo-poc/pull/942

<the user's message verbatim>
```

The user's text is passed through unmodified after the blank line.

When — and only when — the request carries a `pageUrl`, exactly one additional line is
appended after the `PR:` line:

```
[Sent from Graphite — github/acmegizmos/gizmo-poc PR #942]
Title: GIZ-1133: Legacy tally engine retirement #3 - Make the inventory-audit rule widget-backed
Branch: giz-1133-widget-backed-inventory-audit-rule -> main
PR: https://github.com/acmegizmos/gizmo-poc/pull/942
Page: https://app.graphite.com/github/pr/acmegizmos/gizmo-poc/942/GIZ-1133-...

<the user's message verbatim>
```

When the target workspace is on a branch **other** than the PR's head branch — the normal case
for one-workspace-per-stack — exactly two more lines are appended, after `PR:` and any `Page:`:

```
Workspace branch: giz-1132-retire-legacy-cache-flag (NOT this PR's branch)
Note: this worktree is on a different branch of the same stack. If your change belongs to PR #942, check out giz-1133-widget-backed-inventory-audit-rule first.
```

When the bridge also knows that branch's own pull request is **merged** or **closed**, the same
two lines say so instead, because "a different branch of the same stack" reads as a live sibling
and a merged branch is behind by construction — the stack has been restacked past it:

```
Workspace branch: giz-1132-retire-legacy-cache-flag (NOT this PR's branch; its own pull request is already merged)
Note: this worktree is on a branch of this stack whose pull request has already been merged, so it may be behind the rest of the stack. If your change belongs to PR #942, check out giz-1133-widget-backed-inventory-audit-rule first.
```

and, for a pull request closed without merging:

```
Workspace branch: giz-1132-retire-legacy-cache-flag (NOT this PR's branch; its own pull request was closed without merging)
Note: this worktree is on a branch of this stack whose pull request was closed without merging, so it may be behind the rest of the stack. If your change belongs to PR #942, check out giz-1133-widget-backed-inventory-audit-rule first.
```

The advice is identical in all three; only the description of where the agent is standing
changes. When the state cannot be established the first, generic wording is used, which is never
wrong — only less specific.

Without them the agent would be told it is on the PR's branch while the worktree is checked out
elsewhere, and could commit to the wrong branch. The lines are omitted when the branches match
and when the branch cannot be determined; nothing is guessed.

These prompt lines are plugin **behaviour**, not wire shape — the extension never parses the
composed prompt — so `contract` stays at 1. Both verification suites were re-run when the first
form landed; the merged/closed wording was verified on the plugin side only (see
`plugin/VERIFICATION.md` §19), because it changes no wire field the extension reads.

With `pageUrl` absent the header is byte-for-byte the first form above. This is the only way
`pageUrl` affects anything.

### Agent metadata

- `config`: `{ provider, modeId?, thinkingOptionId? }`. `provider` is always the
  `provider/model` pair. `modeId` is omitted only when the resolution chain above ends at step 5.
  `thinkingOptionId` is copied from the followed profile, and **only** when the send actually
  landed on that profile's own `provider/model` — thinking options are per model.
- `title`: `PR #942 · <first line of prompt, trimmed to 60 chars>`
- `labels`:
  ```
  send-to-paseo/pr     = "github:acmegizmos/gizmo-poc#942"
  send-to-paseo/origin = "graphite"
  ```

Always creates a **new** agent — never reuses or messages an existing one.

## Clarifications

Resolved after the first round of implementation, when both sides found these underspecified:

- **`prompt` length** is measured in Unicode code points after trim (1..16000), independent of the
  64 KiB byte cap on the body. Both limits apply; whichever trips first wins. A prompt inside the
  code-point limit that exceeds 64 KiB as UTF-8 gets `payload_too_large`, not `bad_request`.
- **`error.message`** is plain prose with no markup. Put shell commands in `hint`, bare
  (`gh auth login`, not backticked) — the extension is responsible for presentation.
- **Rate limiting** is keyed on the `Origin` header when present, and on the remote address
  otherwise, so a `curl` flood can't consume the extension's budget.
- **`defaultCandidateIndex`** must be a valid index into `candidates`. If the bridge cannot
  determine a sensible default it points at the `create` candidate, never out of range.
- **`contract` mismatch**: the extension compares `contract` from `/v1/ping` against the value it
  was built for. On mismatch it must refuse to send and tell the user to update, rather than
  guessing. `contract` only increments on a breaking change; additive fields do not bump it.
- **Additive fields** may be added to **responses *and* requests** at any time without bumping
  `contract`. Both sides ignore unknown fields.

  The request half is mechanical, not a hope: `SendRequestSchema` and `ResolveRequestSchema`
  extend a non-strict `z.object`, so a plugin that predates a request field **strips** it during
  validation instead of rejecting the body. The failure mode of a request field the other side
  has never heard of is therefore "silently ignored", not "hard break" — the send still
  succeeds, it just falls back to the old behaviour for that one field. The same is true in the
  other direction: an extension that predates a response field never reads it.

  This is what allows a new optional field to ship on one side before the other. It is **not**
  licence to change the meaning of an existing field, to make a new field required, or to
  narrow an existing field's accepted values — any of those is a breaking change and bumps
  `contract`. `modeId` on `/v1/send` and `modes`/`resolvedModeId` on `/v1/ping` and
  `/v1/resolve` were added under this clause, with `contract` staying at **1**.

  `stackPrState` on a `/v1/resolve` candidate was added the same way, and `contract` stays at
  **1** for it too. It is purely additive: the reason and rank vocabularies are unchanged, a
  merged stack branch is still `reason: "stack"` / `rank: 2`, the field is omitted for the `open`
  state an older extension already assumes, and an extension that has never heard of it simply
  does not read it. What *did* change is plugin behaviour — which workspaces qualify as rank 2,
  how rank-2 candidates are ordered among themselves, and two sentences of the composed prompt —
  and none of that is wire shape. `stackPrNumber` also became genuinely optional on a rank-2
  candidate rather than merely documented as such; it was already declared optional, so nothing
  narrowed.

## Test mode (how the extension is testable without Chrome)

The plugin accepts `SEND_TO_PASEO_DRY_RUN=1` in its environment. When set, `POST /v1/send`
performs full resolution and validation but creates nothing, returning the same 200 shape with
`"dryRun": true` and synthetic `agentId`/`workspaceId`. This lets the extension's end-to-end
test drive a real bridge without spawning agents.
